# 공지사항 팀·주제 분류 고도화 기획

## 1. 목표

공지사항을 `공통`, `개발팀`, `비즈니스팀`으로 먼저 나누고, 각 팀 안에서 주제별로 다시 탐색할 수 있게 한다. 팀과 주제를 데이터에서 분리해 한 공지가 어느 조직의 어떤 내용인지 명확히 표현한다.

기존 공지의 분류는 개발자가 임의로 결정하지 않고 관리자가 확인해 저장한다.

원격 `main`은 `NoticesContent.tsx`, 공지 상세, 관리자 공지 화면의 디자인 토큰을 최신 형식으로 변경했다. 공지 고도화는 현재 로컬 화면이 아니라 최신 `main`의 공지 코드를 기준으로 시작한다.

## 2. 분류 체계 초안

| 팀 | 주제 |
| --- | --- |
| 공통 | 운영, 모집, 행사 |
| 개발팀 | 해커톤, 기술 이슈, 개발 스터디, 기술 리서치 |
| 비즈니스팀 | 금융 소식, 아이디어톤, 산업 리서치, 파트너십 |

팀은 `team`, 주제는 `topic`으로 저장한다. `개발팀-해커톤` 같은 하나의 문자열로 합치지 않는다. 최종 명칭과 추가·삭제 가능 여부는 운영진 확인 후 확정한다.

## 3. 사용자 시나리오

### 방문자

1. 공지 목록에 들어오면 전체 또는 공통 공지를 본다.
2. 상단 탭에서 공통·개발팀·비즈니스팀을 선택한다.
3. 두 번째 줄에서 해당 팀의 주제를 선택한다.
4. 검색어와 페이지를 함께 사용한다.
5. 공지 상세를 본 후 뒤로 가도 분류·검색·페이지가 유지된다.

### 관리자

1. 공지를 작성할 때 팀을 선택한다.
2. 선택한 팀에 허용된 주제만 두 번째 선택 상자에 표시된다.
3. 제목, 작성자, 날짜, 본문, 이미지와 함께 저장한다.
4. 기존 공지는 분류되지 않은 목록에서 하나씩 확인해 팀과 주제를 지정한다.

## 4. 경로와 URL 상태

목록 경로는 기존 `/notices`를 유지한다.

예시:

```text
/notices?team=development&topic=hackathon&q=solidity&page=2
```

- `team`: `all | common | development | business`
- `topic`: 선택한 팀에 속하는 값 또는 `all`
- `q`: 검색어
- `page`: 1 이상의 정수

잘못된 값은 오류 화면 대신 안전한 기본값으로 정규화한다. 팀을 바꾸면 기존 팀에만 속한 주제 선택은 `all`로 초기화한다. 검색 또는 분류가 바뀌면 페이지는 1로 돌아간다.

## 5. 화면 구성

### 목록

- 제목과 검색 입력
- 1차 탭: 전체, 공통, 개발팀, 비즈니스팀
- 2차 주제 필터
- 결과 개수
- PC·태블릿: 현재 표 레이아웃을 개선해 유지
- 모바일: 제목, 팀·주제 배지, 날짜가 읽기 쉬운 카드 목록
- 페이지 이동
- 빈 결과와 필터 초기화

### 상세

- 팀과 주제 배지
- 제목, 작성자, 날짜
- 본문과 이미지
- 목록으로 돌아가기 시 기존 검색 매개변수 보존
- 이전·다음 공지는 후속 범위로 둘 수 있다.

### 관리자 폼

- 팀 선택
- 팀에 따라 달라지는 주제 선택
- 필수값 오류 메시지
- 기존 제목·본문·이미지 입력 기능 유지
- 분류되지 않은 기존 공지 표시와 일괄 작업용 필터

## 6. 컴포넌트 구조

```text
NoticesPage (Server)
├── NoticeSearchForm (Client)
├── NoticeTeamTabs (Client)
├── NoticeTopicFilter (Client)
├── NoticeList
│   ├── NoticeTable
│   └── NoticeCardList
└── NoticePagination

NoticeDetailPage (Server)
└── NoticeDetail

AdminNoticesPage (Server)
└── AdminNoticesManager (Client)
    └── NoticeForm
        ├── NoticeTeamSelect
        └── NoticeTopicSelect
```

팀별 주제 목록은 한 곳의 상수와 타입에서 관리해 공개 필터와 관리자 폼이 서로 다른 값을 사용하지 않게 한다.

## 7. 데이터 마이그레이션

현재 `notice.category` 문자열은 바로 삭제하지 않는다.

원격 모집 브랜치가 `013_create_recruitment_system.sql`을 사용하고 있으므로 해당 브랜치가 병합되면 공지 분류 마이그레이션은 `014` 이후의 비어 있는 번호를 사용한다. `database/migrations`와 `supabase/migrations` 중 어느 경로가 실제 배포 기준인지도 작성 전에 확정한다.

1. `team` nullable 컬럼과 `topic` nullable 컬럼을 추가한다.
2. 허용값 검증과 조회 인덱스를 추가한다.
3. 관리자 화면에서 미분류 공지를 식별한다.
4. 운영 관리자가 기존 공지의 팀·주제를 지정한다.
5. 모든 공지 분류가 끝나면 새 글에 두 값을 필수로 만든다.
6. 이전 `category` 제거 여부는 별도 마이그레이션에서 결정한다.

권장 인덱스:

- `(team, topic, date desc)`
- 검색 성능은 데이터 증가 후 실제 쿼리를 측정해 전문 검색 인덱스를 검토한다.

기존 분류를 임의의 기본값으로 덮어 잘못 표시하지 않는다. 전환 기간에는 미분류 공지를 `기존 공지` 또는 `분류 확인 중`으로 명확히 표시한다.

## 8. 타입과 데이터 계약

```ts
type NoticeTeam = 'common' | 'development' | 'business';

type NoticeTopic =
  | 'operation'
  | 'recruitment'
  | 'event'
  | 'hackathon'
  | 'technical-issue'
  | 'development-study'
  | 'technical-research'
  | 'finance-news'
  | 'ideathon'
  | 'industry-research'
  | 'partnership';
```

화면에는 번역된 라벨을 보여주고 DB와 URL에는 안정적인 영문 키를 저장한다. API는 팀에 속하지 않는 주제 조합을 거부한다.

공지 조회 함수는 다음 입력을 받도록 확장한다.

- `team?`
- `topic?`
- `query?`
- `page`
- `pageSize`

응답에는 목록과 전체 개수를 함께 제공해 페이지 수를 계산한다.

## 9. 서버·클라이언트 경계

- 목록 데이터 조회와 상세 조회: Server Component
- 탭·주제·검색 입력: URL을 갱신하는 Client Component
- 관리자 폼: Client Component
- 공지 생성·수정·삭제: 기존 관리자 Route Handler를 확장
- 팀·주제 조합 검증: 클라이언트와 서버 모두 수행, 서버 결과가 최종 기준

필터 결과 전체를 브라우저로 받아 `filter()` 하는 대신 서버 쿼리에서 필터링한다. 데이터가 늘어도 불필요한 전송이 생기지 않게 한다.

## 10. 반응형·접근성

- 팀 탭은 키보드로 이동 가능해야 하며 현재 선택 상태를 텍스트와 시각 표시로 함께 제공한다.
- 단순 링크 필터라면 억지로 ARIA tab 역할을 붙이지 않고 실제 링크 의미를 유지한다.
- 모바일에서 표를 억지로 축소하지 않고 카드 레이아웃으로 전환한다.
- 긴 제목은 중요한 내용이 지나치게 잘리지 않게 최대 줄 수를 정한다.
- 검색 입력에는 보이는 라벨 또는 접근 가능한 이름을 제공한다.
- 결과 변경 시 페이지 제목이나 결과 설명을 통해 현재 조건을 알 수 있게 한다.
- 최신 `Academic Monolith` 디자인 토큰만 사용하고 원격 Playwright 검사에 공지 목록의 1440px·390px 상태를 추가한다.

## 11. 상태 처리

- 결과 없음: 선택 팀·주제·검색어 표시와 초기화 버튼
- 서버 오류: 빈 결과로 위장하지 않고 오류 안내와 재시도
- 잘못된 페이지: 마지막 페이지 또는 1페이지로 안전하게 이동
- 저장 중: 중복 제출 방지
- 분류 미선택: 해당 입력 가까이에 오류 문구
- 미분류 기존 공지: 관리자에게만 눈에 띄는 상태 표시

## 12. 완료 조건

- 공통·개발팀·비즈니스팀과 각 주제를 조합해 필터링할 수 있다.
- 필터, 검색, 페이지가 URL에 남고 새로고침·공유·뒤로 가기가 동작한다.
- 모바일에서는 표가 아닌 읽기 쉬운 목록으로 표시된다.
- 상세 페이지에서 팀과 주제를 확인할 수 있다.
- 관리자는 팀과 유효한 주제를 지정해야 공지를 저장할 수 있다.
- 기존 공지는 관리자 확인 전 잘못된 분류로 공개되지 않는다.
- 현재 공지 상세와 이미지 표시는 회귀 없이 동작한다.
- 비관리자의 쓰기 API 접근은 계속 차단된다.
- 신입 회원 모집 관리자 메뉴와 기존 관리자 공지 메뉴가 함께 있을 때 내비게이션이 깨지지 않는다.
- 원격 Playwright 설정에서 공지 목록의 PC·모바일 회귀 검사가 통과한다.
