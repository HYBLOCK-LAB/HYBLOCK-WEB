# HYBLOCK 홈페이지 콘텐츠 탐색 고도화 기획안

## 1. 제안 요약

HYBLOCK 홈페이지에 축적된 활동 사진과 공지를 사용자가 더 빠르게 이해하고 찾을 수 있도록 정보 구조를 정리한다.

이번 고도화는 다음 두 가지에 집중한다.

1. 사진 28장을 활동 7개 단위의 앨범으로 묶고, 연도·월·분류별로 탐색하게 한다.
2. 공지를 `팀`과 `주제`로 나눠 검색·필터·관리 기준을 명확하게 만든다.

기능을 한 번에 크게 공개하지 않고, 활동 앨범과 공지 분류를 독립된 PR로 나눠 검토·배포한다. 현재 활동 앨범 목록과 상세 화면은 MVP가 구현된 상태이며, 공지 분류는 별도 브랜치에서 검토할 수 있다.

## 2. 추진 배경

### 활동

- 기존 화면은 실제 활동이 아니라 사진 한 장을 카드 한 개로 표시한다.
- 같은 행사명이 여러 번 반복돼 어떤 활동이 있었는지 파악하기 어렵다.
- 날짜가 없는 기록이 같은 수준으로 섞여 시간 순서가 불분명하다.
- 모바일에서 긴 필터가 잘리고, 28개 카드를 계속 내려봐야 한다.

### 공지

- 현재 `category` 문자열 하나에 조직과 내용의 의미가 섞여 있다.
- 사용자는 개발팀 공지인지, 해커톤 공지인지 한 번에 구분하기 어렵다.
- 관리자도 분류 기준을 일관되게 적용하기 어렵다.
- 검색, 필터, 페이지 상태가 URL에 남지 않으면 공유와 뒤로 가기 경험이 불안정하다.

## 3. 목표

### 사용자 목표

- 활동 페이지에서 사진보다 활동 단위를 먼저 이해한다.
- 연도와 월, 활동 분류로 원하는 기록을 좁힌다.
- 앨범 상세에서 설명과 전체 사진을 확인한다.
- 공지를 팀과 주제로 좁히고 검색 조건을 공유할 수 있다.

### 운영 목표

- 관리자가 앨범의 대표 사진, 설명, 날짜, 공개 상태를 관리한다.
- 관리자가 공지 작성 시 유효한 팀·주제 조합만 선택한다.
- 기존 데이터를 임의 분류하지 않고 운영진 확인을 거쳐 이전한다.
- 공개 화면과 관리자 화면이 같은 데이터 계약과 명칭을 사용한다.

## 4. 범위

### 포함

| 영역 | 1차 제공 내용 |
| --- | --- |
| 활동 목록 | 카테고리 필터, 연도·월 그룹, 앨범 카드, 날짜 미정 구역 |
| 활동 상세 | 제목, 설명, 날짜, 분류, 대표 사진, 전체 사진 |
| 활동 관리 | 앨범 생성·수정, 다중 사진 업로드, 대표 사진, 게시 상태 |
| 공지 목록 | 팀 탭, 주제 필터, 검색, 페이지, 결과 개수 |
| 공지 상세 | 팀·주제 표시, 목록 조건 보존 |
| 공지 관리 | 팀·주제 입력, 조합 검증, 미분류 공지 확인 |
| 공통 품질 | 390px·768px·1440px 반응형, 키보드 접근, 오류·빈 상태 |

### 제외

- 활동 사진 확대용 라이트박스
- 활동 댓글·좋아요
- 공지 이전·다음 글
- 인증 체계 재설계
- 신입 회원 모집 시스템 변경

## 5. 사용자 흐름

### 활동 방문자

1. `/activities`에서 최신 연도와 월을 확인한다.
2. 카테고리를 선택해 앨범을 좁힌다.
3. 카드에서 대표 사진, 활동명, 날짜, 사진 수를 확인한다.
4. `/activities/[slug]`에서 설명과 전체 사진을 본다.
5. 목록으로 돌아가 탐색을 이어간다.

### 공지 방문자

1. `/notices`에서 전체 공지를 확인한다.
2. `공통·개발팀·비즈니스팀` 중 하나를 선택한다.
3. 해당 팀의 주제를 선택하고 검색어를 입력한다.
4. 상세를 본 뒤 돌아와도 기존 조건을 유지한다.

### 관리자

1. 콘텐츠 정보와 공개 상태를 입력한다.
2. 서버가 권한과 입력값을 다시 검증한다.
3. 미리보기 또는 목록에서 결과를 확인한다.
4. 삭제보다 비공개 전환을 우선해 운영 기록을 보존한다.

## 6. 정보 구조

```text
/activities
└── /activities/[slug]

/notices
└── /notices/[id]

/admin/activity-albums
/admin/notices
```

기존 `/admin/activities`는 출석 세션 관리 화면이므로 이름과 역할을 유지한다. 새 앨범 관리 화면은 `/admin/activity-albums`로 분리한다.

## 7. 데이터 원칙

- 연도와 월은 별도 컬럼으로 중복 저장하지 않고 활동 날짜에서 계산한다.
- 날짜가 없는 활동은 잘못된 시점에 배치하지 않고 `날짜 확인 중`으로 분리한다.
- 대표 사진은 해당 앨범에 속한 사진만 선택할 수 있다.
- 공지의 `team`과 `topic`은 별도 값으로 저장한다.
- 기존 공지는 운영진 확인 전 임의의 새 분류로 공개하지 않는다.
- 공개 식별자는 사람이 읽을 수 있는 고유 `slug`를 사용한다.

## 8. UX·디자인 기준

- 강한 제목은 페이지 시작점과 주요 연도에만 사용한다.
- 일반 카드에는 큰 그림자와 과한 둥근 모서리를 반복하지 않는다.
- 배지와 필터는 실제 상태·분류 의미가 있을 때만 사용한다.
- 모바일 필터는 잘리는 가로 목록 대신 `select` 또는 줄바꿈을 사용한다.
- 이미지 비율을 미리 확보하고, 첫 화면 대표 이미지만 우선 로딩한다.
- 성공·실패·빈 결과는 색상뿐 아니라 문장으로 설명한다.
- 모든 링크와 입력은 키보드 포커스가 보여야 하며 터치 영역은 약 44px 이상으로 둔다.

## 9. 기술·보안 기준

- 최초 목록·상세 조회는 Server Component를 우선한다.
- 필터와 폼처럼 상호작용이 필요한 부분만 Client Component로 둔다.
- 쓰기 API는 관리자 세션, 허용값, 소유 관계를 서버에서 검증한다.
- 서비스 역할 키와 관리자 권한 정보는 클라이언트 번들에 포함하지 않는다.
- URL 필터 값은 허용 목록으로 정규화하고 잘못된 값은 안전한 기본값으로 처리한다.
- 타입은 데이터 계층에서 정의하고 공개 화면과 관리자 화면이 함께 사용한다.

## 10. 단계별 배포

| 단계 | 내용 | 완료 기준 |
| --- | --- | --- |
| 1 | 활동 앨범 정적 MVP | 7개 앨범 목록·상세, 필터, 모바일 검수 |
| 2 | 공지 팀·주제 MVP | URL 기반 필터·검색, 상세·관리자 분류 |
| 3 | 운영 데이터 이전 | 운영진 검수, Storage 업로드, DB 전환 |
| 4 | 관리자 앨범 기능 | 업로드·정렬·대표 사진·게시 상태 |
| 5 | 회귀 점검·배포 | 빌드, 디자인 테스트, 권한별 시나리오 통과 |

각 단계는 독립적으로 되돌릴 수 있게 PR을 나눈다. 정적 데이터는 DB 전환이 확인되기 전까지 제거하지 않는다.

## 11. 검수 기준

- 390px, 768px, 1440px에서 가로 넘침과 잘린 컨트롤이 없다.
- 같은 활동의 사진이 목록에서 개별 카드로 반복되지 않는다.
- 날짜가 없는 앨범은 별도 구역에만 표시된다.
- 잘못된 상세 URL은 404로 처리된다.
- 이미지 대체 텍스트와 논리적인 제목 구조를 제공한다.
- 필터 결과가 없을 때 현재 상태와 다음 행동을 안내한다.
- 공지 필터·검색·페이지가 URL과 뒤로 가기에 유지된다.
- 비관리자는 쓰기 API를 사용할 수 없다.
- 타입 검사와 프로덕션 빌드, 디자인 회귀 검사가 통과한다.

## 12. 팀 확인이 필요한 항목

1. 날짜 미정인 네 개 활동의 실제 일자
2. 각 앨범의 대표 사진과 공개 가능 여부
3. 활동 설명의 최종 한국어·영어 문구
4. 공지 팀·주제 명칭과 향후 추가 권한
5. 실제 운영 DB 마이그레이션 경로와 번호
6. 이미지 용량·개수 제한과 보관 정책
