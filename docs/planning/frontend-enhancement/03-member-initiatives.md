# 회원 프로젝트·스터디 제안 및 모집 기획

## 1. 목표

활성 회원이 학회 내 자율 프로젝트나 스터디를 직접 제안하고, 다른 회원이 사이트 안에서 지원하게 한다. 별도 관리자 승인 대기 없이 즉시 게시하되, 작성자가 모집 상태와 지원자를 관리하고 관리자는 부적절한 글을 숨길 수 있다.

이 기능은 공지의 하위 분류가 아니라 별도 회원 참여 영역으로 제공한다.

## 2. 신입 회원 모집 시스템과의 구분

원격 `agent/recruitment-system` 브랜치는 비로그인 지원자가 `/apply`에서 신입 회원 지원서를 제출하고 관리자가 평가하는 기능이다. 이번 프로젝트·스터디 기능은 이미 승인된 활성 회원이 `/community`에서 내부 활동 팀원을 모집하는 기능이므로 다음 경계를 유지한다.

| 구분 | 신입 회원 모집 | 프로젝트·스터디 |
| --- | --- | --- |
| 대상 | 비회원 지원자 | 활성 학회원 |
| 공개 경로 | `/apply` | `/community` |
| 관리자 경로 | `/admin/recruitment` | 제안 숨김 관리 영역 |
| 핵심 테이블 | `recruitment_campaign`, `application` | `initiative`, `initiative_application` |
| 결과 처리 | 운영진의 외부 연락 | 사이트 내부 승인·거절 상태 |

메뉴와 문구에서는 신입 회원의 `지원`과 내부 활동의 `참여 지원`이 혼동되지 않게 구분한다. 신입 모집 테이블·API·평가 흐름은 이번 구현에서 수정하지 않는다.

## 3. 핵심 정책

- 글 유형: 프로젝트, 스터디
- 게시 자격: 로그인된 활성 회원
- 게시 방식: 작성 완료 즉시 게시
- 지원 방식: 사이트 내부 지원서
- 지원 처리: 작성자가 승인 또는 거절
- 모집 상태: 모집 중, 진행 중, 종료
- 운영 관리: 관리자가 글을 숨김 처리할 수 있음
- 작성·지원자 개인정보: 공개 목록에 노출하지 않음

회원 목록·상세의 공개 범위는 팀 확인이 필요하다. 개인정보 보호와 학회 내부 기능이라는 목적을 고려한 기본안은 로그인된 활성 회원만 접근하는 것이다.

원격 `main`에서는 일반 회원 로그인 화면이 임시 폐쇄되어 있고 모집 브랜치도 관리자 로그인만 예외적으로 허용한다. 따라서 일반 회원 로그인 재개 또는 공식 대체 인증 경로가 확정되기 전에는 이 기능을 운영에 노출하지 않는다.

## 4. 사용자 시나리오

### 제안 작성자

1. 로그인 후 프로젝트·스터디 목록에 들어간다.
2. `새 제안 만들기`를 누른다.
3. 유형, 제목, 한 줄 소개, 상세 내용, 모집 역할, 인원, 일정을 입력한다.
4. 미리 확인하고 즉시 게시한다.
5. 상세 페이지에서 지원자 목록을 본다.
6. 지원자의 희망 역할과 메시지를 확인해 승인 또는 거절한다.
7. 모집을 마치면 `진행 중` 또는 `종료`로 바꾼다.

### 지원 회원

1. 유형·상태·태그로 모집 글을 찾는다.
2. 상세 페이지에서 설명, 일정, 필요한 역할, 남은 인원을 확인한다.
3. 희망 역할과 지원 메시지를 작성해 지원한다.
4. 내 지원 상태를 확인한다.
5. 아직 처리되지 않은 지원은 취소할 수 있다.

### 관리자

1. 신고 또는 운영 판단이 필요한 글을 확인한다.
2. 숨김 사유를 기록하고 공개 목록에서 숨긴다.
3. 복구 정책에 따라 다시 공개할 수 있다.

신고 기능 자체는 1차 범위에서 제외하고 운영진의 관리자 화면 접근으로 처리한다.

## 5. 경로와 화면

### `/community`

- 프로젝트·스터디 소개
- 새 제안 만들기 버튼
- 유형 필터: 전체, 프로젝트, 스터디
- 상태 필터: 모집 중, 진행 중, 종료
- 태그 또는 키워드 검색
- 제안 카드 목록
- 내가 만든 제안, 내가 지원한 제안으로 가는 진입점

카드 정보:

- 유형과 상태 배지
- 제목과 한 줄 소개
- 작성자 표시명
- 모집 역할
- 모집 인원과 승인 인원
- 마감일 또는 상시 모집
- 생성일

### `/community/new`

- 유형
- 제목
- 한 줄 소개
- 상세 설명
- 태그
- 필요한 역할 목록
- 모집 인원
- 진행 방식·일정
- 시작 예정일과 모집 마감일
- 취소, 게시 버튼

### `/community/[id]`

- 제안 상세 내용
- 모집 상태와 남은 자리
- 작성자에게만 수정·상태 변경·지원자 관리 버튼
- 다른 활성 회원에게만 지원 폼
- 본인 글에는 지원 버튼을 표시하지 않음
- 이미 지원했다면 현재 상태와 가능한 취소 동작 표시
- 숨김·없는 글은 권한에 맞는 오류 처리

### `/community/[id]/edit`

- 작성자만 접근
- 기존 값이 채워진 폼
- 이미 승인된 지원자가 있다면 모집 인원을 그보다 작게 낮출 수 없음
- 유형 변경 허용 여부는 1차 구현 전에 결정

## 7. 데이터 구조

### `initiative`

| 필드 | 형식 | 설명 |
| --- | --- | --- |
| `id` | bigint | 식별자 |
| `type` | project/study | 제안 유형 |
| `title` | text | 제목 |
| `summary` | text | 카드용 한 줄 소개 |
| `description` | text | 상세 내용 |
| `author_member_id` | member FK | 서버가 현재 회원으로 지정 |
| `tags` | text[] | 탐색용 태그 |
| `required_roles` | text[] | 모집 역할 |
| `capacity` | integer nullable | 전체 모집 인원, null은 미정 |
| `schedule` | text nullable | 진행 일정·방식 |
| `start_date` | date nullable | 시작 예정일 |
| `recruitment_deadline` | date nullable | 모집 마감일 |
| `status` | recruiting/in_progress/closed | 진행 상태 |
| `hidden_at` | timestamptz nullable | 관리자 숨김 여부 |
| `hidden_reason` | text nullable | 운영 기록 |
| `created_at`, `updated_at` | timestamptz | 감사 정보 |

### `initiative_application`

| 필드 | 형식 | 설명 |
| --- | --- | --- |
| `id` | bigint | 지원 식별자 |
| `initiative_id` | initiative FK | 지원 대상 |
| `applicant_member_id` | member FK | 서버가 현재 회원으로 지정 |
| `desired_role` | text | 희망 역할 |
| `message` | text | 지원 메시지 |
| `status` | pending/accepted/rejected/withdrawn | 지원 상태 |
| `created_at`, `updated_at` | timestamptz | 감사 정보 |

제약 조건:

- 한 회원은 같은 제안에 한 번만 지원할 수 있다.
- 작성자는 자기 글에 지원할 수 없다.
- 모집 중인 글에만 새 지원을 만들 수 있다.
- 승인 인원은 모집 인원을 넘을 수 없다.
- 숨겨진 글에는 새 지원을 만들 수 없다.
- `author_member_id`와 `applicant_member_id`는 요청 본문이 아니라 인증 결과에서 가져온다.

DB 마이그레이션은 원격 모집 시스템의 `013` 이후 비어 있는 번호를 사용한다. 모집 브랜치가 추가한 두 마이그레이션 경로 중 실제 운영 기준을 먼저 확인하고, 같은 SQL을 두 경로에 임의로 중복 생성하지 않는다.

## 8. 인증과 권한 구현

현재 프로젝트에는 지갑 세션 쿠키와 Google 로그인 토큰을 회원 레코드로 연결하는 흐름이 있다. 이를 바탕으로 재사용 가능한 서버 도우미를 추가한다.

구현 시작 시점에는 모집 브랜치가 변경한 최신 `wallet-session.ts`와 관리자 전용 로그인 예외를 먼저 반영한다. 해당 파일을 이전 버전으로 되돌리거나 신입 모집 인증 동작을 제거하지 않는다.

```text
requireActiveMemberApiAccess(request)
├── 기존 지갑 서버 세션 확인
├── 없으면 Google/Supabase Bearer 토큰 확인
├── wallet_address로 member 조회
└── is_active 확인 후 회원 반환
```

권한 표:

| 동작 | 활성 회원 | 작성자 | 관리자 |
| --- | --- | --- | --- |
| 목록·상세 조회 | 허용 | 허용 | 허용 |
| 새 제안 | 허용 | 허용 | 허용 |
| 본인 외 제안 수정 | 금지 | 본인만 허용 | 정책상 필요 시 별도 관리 동작 |
| 지원 | 타인 글에 허용 | 자기 글에는 금지 | 타인 글이면 동일 |
| 지원 승인·거절 | 금지 | 허용 | 운영 정책 확인 |
| 글 숨김·복구 | 금지 | 금지 | 허용 |

서비스 역할 키로 DB에 접근하면 RLS가 우회될 수 있으므로 Route Handler의 권한 검사가 필수다. RLS도 방어 계층으로 정의하지만 클라이언트에서 직접 쓰기 권한을 주지 않는다.

## 9. API 계약

### 제안

- `GET /api/initiatives?type=&status=&q=&page=`
- `POST /api/initiatives`
- `GET /api/initiatives/[id]`
- `PATCH /api/initiatives/[id]`
- `POST /api/initiatives/[id]/close`
- `POST /api/admin/initiatives/[id]/hide`
- `POST /api/admin/initiatives/[id]/restore`

### 지원

- `POST /api/initiatives/[id]/applications`
- `GET /api/initiatives/[id]/applications` — 작성자만 전체 조회
- `PATCH /api/initiatives/[id]/applications/[applicationId]` — 작성자의 승인·거절
- `POST /api/initiatives/[id]/applications/[applicationId]/withdraw` — 지원자 본인

상태 변경 API는 요청 시 현재 상태를 다시 확인한다. 두 번 클릭이나 동시에 승인하는 상황에서도 정원을 넘지 않도록 DB 트랜잭션 또는 원자적 검증을 사용한다.

## 10. 입력 검증 초안

- 제목: 2~80자
- 한 줄 소개: 10~160자
- 상세 설명: 20~5000자
- 역할: 1개 이상, 각 2~30자
- 태그: 최대 5개, 각 2~20자
- 모집 인원: 1~100 또는 미정
- 지원 메시지: 10~1000자
- 모집 마감일은 제안 등록일보다 과거일 수 없음
- 시작일과 마감일의 선후 관계를 검증

정확한 제한값은 운영진 확인 후 상수로 관리하고 클라이언트·서버가 같은 기준을 사용한다.

## 11. 상태 처리

- 비로그인: 로그인 필요 이유와 로그인 진입점 제공
- 비활성 회원: 일반 오류가 아니라 회원 승인 상태 안내
- 목록 없음: 첫 제안을 만들 수 있는 안내
- 필터 결과 없음: 조건 초기화
- 저장 중: 버튼 비활성화와 진행 문구
- 중복 지원: 현재 지원 상태 표시
- 모집 종료: 지원 폼 대신 종료 안내
- 승인 충돌: 최신 정원 상태를 다시 불러오고 설명
- 권한 없음: 존재를 숨겨야 하는 경우와 단순 금지 상황을 구분
- 숨김 글: 일반 회원 목록·상세에서 제외, 관리자에게 사유 표시
- 일반 로그인 점검 중: 사용할 수 없는 작성·지원 버튼을 보여주기보다 회원 기능 준비 상태와 운영 안내를 표시

## 12. 반응형·접근성

- 1440px: 필터와 목록, 상세와 보조 정보를 넓게 배치하되 지원자 정보는 작성자에게만 표시
- 768px: 두 열 카드를 기본으로 하고 상세의 보조 영역을 아래로 이동
- 390px: 한 열 카드, 하단의 주요 지원 버튼이 내용을 가리지 않도록 배치
- 모든 입력에 연결된 라벨과 오류 설명 제공
- 역할 추가·삭제 버튼의 목적을 스크린 리더가 알 수 있게 이름 지정
- 상태 배지는 색상 외에 `모집 중`, `승인됨` 같은 텍스트 포함
- 확인이 필요한 승인·거절·모집 종료 동작에는 명확한 확인 문구 제공
- 포커스를 잃는 갑작스러운 목록 갱신 방지
- 최신 `Academic Monolith` 토큰을 사용하고 원격 Playwright 설정에 목록·상세·작성 화면의 1440px·390px 검사를 추가

## 13. 개인정보와 운영 안전

- 일반 목록에는 지갑 주소, 이메일, 전화번호를 표시하지 않는다.
- 지원 메시지와 지원자 정보는 해당 제안 작성자, 지원자 본인, 필요한 관리자만 본다.
- API 오류에 내부 DB 정보나 토큰을 포함하지 않는다.
- HTML 입력을 그대로 렌더링하지 않고 안전한 텍스트 또는 검증된 마크다운만 허용한다.
- 숨김은 삭제와 구분해 운영 기록을 남긴다.
- 즉시 게시이므로 이용 규칙과 관리자 숨김 기준을 게시 폼 가까이에 안내한다.

## 14. 완료 조건

- 활성 회원이 프로젝트 또는 스터디를 작성하면 즉시 목록에 나타난다.
- 유형·상태·검색 필터가 URL과 함께 동작한다.
- 작성자는 본인 글만 수정하고 모집 상태를 바꿀 수 있다.
- 다른 활성 회원은 모집 중인 글에 사이트 안에서 한 번만 지원할 수 있다.
- 작성자는 지원자를 승인·거절하고 지원자는 처리 전 지원을 취소할 수 있다.
- 모집 인원을 초과한 승인은 서버에서 차단된다.
- 비로그인·비활성 회원·권한 없는 사용자의 쓰기 요청이 차단된다.
- 관리자는 글을 숨기고 복구할 수 있다.
- 지원자 개인정보가 공개 응답이나 화면에 노출되지 않는다.
- 1440px, 768px, 390px에서 작성·조회·지원·관리 흐름을 완료할 수 있다.
- 일반 회원의 공식 로그인 경로가 열려 있고 활성 회원 판별 흐름이 실제 환경에서 검증된다.
- `/apply` 신입 지원과 `/admin/recruitment` 평가 기능이 그대로 동작한다.
- 프로젝트·스터디 핵심 화면이 원격 Playwright 디자인 회귀 검사를 통과한다.
