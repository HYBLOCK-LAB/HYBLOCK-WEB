# 김민서_하이블록홈페이지작업기획제안서

> HYBLOCK 콘텐츠 탐색·회원 참여 고도화

- 문서 상태: 기능 범위 확정안

## 1. 프로젝트 목표

현재 HYBLOCK 사이트에서 서로 흩어진 활동 기록과 공지를 더 쉽게 탐색하게 만들고, 회원이 프로젝트·스터디를 직접 제안하고 모집할 수 있는 참여 흐름을 추가한다.

이번 고도화는 다음 세 기능을 범위로 삼는다.

1. 활동별 앨범 고도화
2. 공지사항 팀·주제 분류 고도화
3. 회원 프로젝트·스터디 제안 및 모집 기능

## 2. 현재 코드와의 연결

| 영역 | 현재 상태 | 이번 구현 방향 |
| --- | --- | --- |
| 활동 | `site-content.ts`의 사진 28장을 한 목록으로 표시 | 연도 → 월 → 활동 앨범으로 탐색하고 상세 페이지 제공 |
| 활동 관리 | `/admin/activities`는 출석 세션 관리 화면 | 기존 화면은 유지하고 앨범 관리 화면을 별도로 추가 |
| 공지 | `notice.category` 문자열 하나로 분류 | `team`과 `topic`을 분리하고 두 단계 필터 제공 |
| 공지 관리 | 관리자만 공지 CRUD 가능 | 기존 권한을 유지하며 팀·주제 선택 기능 추가 |
| 회원 기능 | 활성 회원 조회와 관리자 인증 기반은 있으나 일반 로그인 화면은 임시 폐쇄 상태 | 로그인 재개 조건을 먼저 확정한 뒤 활성 회원 전용 제안·지원 API와 화면 추가 |

## 3. 원격 저장소 통합 기준

2026-07-22에 확인한 구현 기준은 `origin/main`의 `2ea2a29`이다. 현재 로컬 활동 브랜치는 이 기준과 갈라져 있으므로 새 구현을 시작하기 전에 최신 `main`을 기준으로 활동 코드를 옮기거나 충돌을 수동 해결해야 한다.

- 최신 원격에는 `DESIGN.md`와 Playwright 디자인 회귀 검사가 추가됐다.
- Tailwind 디자인 토큰은 `surface-lowest`, `on-surface-muted`처럼 kebab-case 이름을 사용한다.
- 현재 활동 브랜치와 원격은 `ActivitiesGallery.tsx`에서 실제 병합 충돌이 발생한다.
- 원격 `agent/recruitment-system` 브랜치는 신입 회원 지원·평가 시스템이며 내부 프로젝트·스터디와는 별도 기능이다.
- 모집 브랜치가 `013_create_recruitment_system.sql`을 사용하므로 이번 기능의 첫 DB 마이그레이션은 해당 브랜치의 병합 여부를 확인한 뒤 다음 번호를 사용한다.
- 모집 브랜치가 `database/migrations`와 `supabase/migrations`를 함께 추가하므로 운영 기준 폴더를 팀에서 먼저 확정한다.

현재 일반 회원 `/login`은 원격 `main`에서 임시 폐쇄돼 있다. 프로젝트·스터디는 화면 구현과 별개로 일반 회원 로그인 재개가 출시 선행 조건이다.

## 4. 사용자와 권한

| 사용자 | 활동 앨범 | 공지 | 프로젝트·스터디 |
| --- | --- | --- | --- |
| 비로그인 방문자 | 게시된 앨범 조회 | 게시된 공지 조회 | 접근 시 로그인 안내 |
| 활성 회원 | 게시된 앨범 조회 | 게시된 공지 조회 | 제안 작성, 지원, 본인 지원 취소 |
| 제안 작성자 | 일반 조회 | 일반 조회 | 본인 글 수정·모집 종료, 지원자 승인·거절 |
| 관리자 | 앨범 생성·사진 업로드·대표 사진 선택 | 공지 생성·수정·분류 | 모든 제안 숨김 처리 및 운영 관리 |

로그인 여부나 관리자 여부는 브라우저 상태만 믿지 않고 서버에서 다시 확인한다. 기존 지갑 세션과 Google 로그인 경로는 재사용하되 인증 체계 자체를 새로 설계하지 않는다. 일반 로그인이 폐쇄된 동안에는 회원 제안 메뉴를 공개 출시하지 않는다.

## 5. 전체 정보 구조

```text
/activities
└── /activities/[slug]

/notices
└── /notices/[id]

/community
├── /community/new
├── /community/[id]
└── /community/[id]/edit

/admin/activity-albums
/admin/notices
```

`/community`는 기존 상단 내비게이션에 별도 메뉴로 추가한다. 한국어 메뉴명은 팀과 협의해 `프로젝트·스터디` 또는 `회원 제안` 중 하나로 확정한다.

## 6. 공통 UX 원칙

- URL로 필터 상태를 표현해 새로고침·공유·뒤로 가기가 자연스럽게 동작해야 한다.
- 데이터가 없을 때, 불러오는 중일 때, 불러오기에 실패했을 때를 서로 다른 화면으로 표시한다.
- 모바일 390px에서 가로 스크롤이나 잘린 필터가 없어야 한다.
- 키보드만으로 메뉴, 필터, 카드, 폼, 상세 페이지를 사용할 수 있어야 한다.
- 카드 전체를 클릭할 수 있게 하되 내부 버튼과 중복 클릭 영역을 만들지 않는다.
- 이미지에는 내용에 맞는 대체 텍스트를 제공하고 크기를 미리 확보해 화면 흔들림을 줄인다.
- 성공·실패 메시지는 색상만으로 전달하지 않고 텍스트와 상태를 함께 제공한다.

## 7. 공통 기술 원칙

- 목록·상세의 최초 데이터 조회는 Server Component를 우선한다.
- 필터, 폼, 탭, 지원 버튼처럼 상호작용이 필요한 작은 영역만 Client Component로 둔다.
- 쓰기 작업은 Route Handler에서 인증·권한·입력값을 다시 검증한다.
- 브라우저가 전달한 회원 ID, 작성자 ID, 관리자 여부를 그대로 신뢰하지 않는다.
- Supabase 서비스 역할 키를 사용하는 서버 코드는 클라이언트 번들에 포함하지 않는다.
- 공개 식별자는 숫자 ID 대신 사람이 읽기 쉬운 `slug`를 우선하되 중복을 방지한다.
- TypeScript 타입은 화면에서 따로 복제하지 않고 데이터 계층 타입에서 파생한다.
- 신규 화면은 원격 `DESIGN.md`의 `Academic Monolith` 규칙과 `web/app/globals.css`의 최신 토큰을 따른다.
- 기존 camelCase Tailwind 토큰을 새 코드에 복사하지 않고 kebab-case 토큰을 사용한다.
- PC 1440px와 모바일 390px Playwright 회귀 검사를 추가하고, 필요한 경우 태블릿 768px 검사를 보강한다.

## 8. 통합 선행 조건

- 모집 시스템 브랜치의 병합 여부와 DB 마이그레이션 기준 경로를 확정한다.
- 일반 회원 로그인 재개 시점과 프로젝트·스터디의 공식 인증 방식을 확정한다.
- 최신 `main`의 디자인 시스템과 기존 활동 아카이브 변경을 함께 반영한다.

## 9. 완료의 공통 기준

- PC 1440px, 태블릿 768px, 모바일 390px에서 주요 흐름을 직접 확인한다.
- 키보드 탐색과 명확한 포커스 표시를 확인한다.
- 비로그인, 일반 회원, 작성자, 관리자 권한별 흐름을 확인한다.
- 타입 검사, 린트, 프로덕션 빌드가 통과한다.
- 새 데이터 마이그레이션의 적용·되돌림 절차를 문서화한다.
- 기존 홈, 출석 관리, 공지 상세, 로그인 흐름에 회귀가 없어야 한다.
- 원격 디자인 회귀 테스트에 활동·공지·회원 제안 핵심 화면을 추가한다.
- 다른 팀의 신입 회원 모집 `/apply`와 관리자 `/admin/recruitment` 흐름에 회귀가 없어야 한다.

## 10. 이번 담당에서 제외할 범위

- 출석 세션, QR 출석, 지갑 연결 자체의 재설계
- SBT, EAS, 스마트 컨트랙트 및 온체인 기능
- 회원 가입·승인 정책과 관리자 권한 정책 변경
- 댓글, 실시간 채팅, 푸시·이메일 알림
- 결제, 참가비, 외부 캘린더 연동
- 전체 홈페이지 디자인 시스템 전면 교체
- 운영 데이터의 임의 작성·삭제 및 기존 공지의 임의 분류
- 배포, 운영 DB 마이그레이션 실행, main 병합
- 신입 회원 지원서 작성·평가 시스템과 `/apply` 화면

## 11. 팀에 먼저 확인할 사항

1. 새 메뉴의 최종 명칭을 `프로젝트·스터디`로 할지 `회원 제안`으로 할지
2. 활동 사진을 저장할 Supabase Storage 버킷과 업로드 용량 정책
3. 기존 28장 사진의 활동명·날짜·대표 사진·대체 텍스트 확정 담당자
4. 공지 팀·주제의 최종 목록과 기존 공지 분류 담당 관리자
5. 프로젝트·스터디 목록과 상세를 회원에게만 보일지, 목록 일부를 공개할지
6. 지원 승인 후 연락처를 공개할지, 사이트 안의 상태 변경만 제공할지
7. 관리자의 제안 숨김 사유와 복구 정책
8. `agent/recruitment-system` 브랜치의 병합 일정과 담당자
9. 일반 회원 로그인 재개 시점과 회원 기능의 공식 인증 방식
10. DB 마이그레이션의 기준 폴더와 이번 기능의 시작 번호
