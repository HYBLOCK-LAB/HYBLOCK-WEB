# 공지사항 팀·주제 분류 상세 기획

## 1. 핵심 결정

공지의 조직 범위와 내용 분류를 한 문자열에 합치지 않고 `team`과 `topic`으로 나눠 저장한다.

| 팀 | 주제 |
| --- | --- |
| 공통 | 운영, 모집, 행사 |
| 개발팀 | 해커톤, 기술 이슈, 개발 세션, 기술 리서치 |
| 비즈니스팀 | 금융 소식, 아이디어톤, 산업 리서치, 파트너십 |

명칭과 허용 주제는 운영진 검토 후 확정한다. 기존 공지를 개발자가 추측해 자동 분류하지 않는다.

## 2. 공개 화면

목록 경로는 `/notices`를 유지하고 필터를 검색 매개변수로 표현한다.

```text
/notices?team=development&topic=hackathon&q=solidity&page=2
```

- `team`: `all | common | development | business`
- `topic`: 선택 팀에 속한 값 또는 `all`
- `q`: 검색어
- `page`: 1 이상의 정수

팀이 바뀌면 기존 팀에만 속한 주제는 `all`로 초기화한다. 검색어나 분류가 바뀌면 1페이지로 돌아간다. 잘못된 값은 오류 대신 안전한 기본값으로 정규화한다.

### 목록

- 검색 입력
- 전체·공통·개발팀·비즈니스팀 1차 필터
- 선택 팀의 주제 2차 필터
- 결과 개수
- 데스크톱 표, 모바일 카드 목록
- 페이지 이동
- 빈 결과와 초기화 안내

### 상세

- 팀과 주제
- 제목, 작성자, 날짜
- 본문과 이미지
- 목록으로 돌아갈 때 기존 검색 조건 유지

## 3. 관리자 화면

- 팀 선택 후 해당 팀에 허용된 주제만 표시
- 팀·주제 필수값 검증
- 미분류 기존 공지 전용 필터
- 저장 중 중복 제출 방지
- 사용자 입력 검증과 동일한 규칙을 서버에서도 재검증

## 4. 데이터 이전

현재 `notice.category`는 즉시 삭제하지 않는다.

1. nullable `team`, `topic` 컬럼을 추가한다.
2. 허용값 제약과 `(team, topic, date desc)` 인덱스를 추가한다.
3. 관리자 화면에서 미분류 공지를 식별한다.
4. 운영진이 각 공지를 확인해 새 분류를 지정한다.
5. 모든 공지가 분류되면 새 글의 두 값을 필수로 전환한다.
6. 기존 `category` 제거는 별도 마이그레이션으로 진행한다.

마이그레이션 번호와 운영 기준 폴더는 작업 시작 전에 원격 저장소의 최신 상태를 확인해 확정한다.

## 5. 데이터 계약

```ts
type NoticeTeam = 'common' | 'development' | 'business';

type NoticeTopic =
  | 'operation'
  | 'recruitment'
  | 'event'
  | 'hackathon'
  | 'technical-issue'
  | 'development-session'
  | 'technical-research'
  | 'finance-news'
  | 'ideathon'
  | 'industry-research'
  | 'partnership';
```

화면에는 번역된 라벨을 보여주고 DB와 URL에는 안정적인 영문 키를 사용한다. API는 팀에 속하지 않는 주제 조합을 거부한다.

## 6. 완료 조건

- 팀과 주제를 조합해 공지를 필터링할 수 있다.
- 검색·필터·페이지가 URL, 새로고침, 공유, 뒤로 가기에 유지된다.
- 모바일에서는 제목과 분류, 날짜를 읽기 쉬운 카드로 표시한다.
- 상세에서 팀과 주제를 확인할 수 있다.
- 관리자는 유효한 팀·주제를 지정해야 저장할 수 있다.
- 기존 공지는 운영진 확인 전 잘못된 새 분류로 노출되지 않는다.
- 비관리자의 쓰기 API 접근은 계속 차단된다.
- 기존 공지 상세와 이미지 표시에 회귀가 없다.
